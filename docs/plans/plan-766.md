## Decisions / risks

- **Sub-task ordering is commit order, and sub-task 1 ships first.** `/attend` is a hard dependency for the whole flow: without it every approved session looks unattended and the cron sends the no-show message to innocent hubers. The card work is worthless without it.
- **Both new types share one card component.** `huberNoShowReadingSession` and `autoCancelReadingSession` are structurally identical — single rich-text line, no title, no CTA, no reason box — and differ only in message key. One component with a key lookup avoids duplicating the #764 card and keeps the two from drifting.
- **Unconfirmed: which `relatedEntity` field carries the Huber name on auto-cancel.** Defaulting to `relatedEntity.humanBook?.fullName` with a `sender.fullName` fallback. If the backend populates only `sender` on an auto-cancel and that is a system/admin account, the card renders the wrong name. Confirm with `hulib-services` before sub-task 3.
- **No copy agreed for `huberNoShowReadingSession`.** No design was supplied and no wording was agreed. A placeholder string will ship and must be flagged in `docs/results/result-766.md` and the PR as needing product sign-off.
- **No Storybook precedent for notification cards.** None of the 9 existing stories cover `src/components/notification/*`, and the #764 commit shipped its card without one. Sub-task 5 must build a mock `Notification` from scratch and satisfy the next-intl provider that `useTranslations('notifications')` requires.
- **Designs are not browser-verified.** The body text in both references reads heavier than #764's `font-medium`; the implemented weight may need adjusting after a real browser look. Sub-tasks 3 and 4 are marked as needing a manual browser check.
- **Server-side prerequisite:** `npx prisma migrate deploy` must run on the backend before `/attend` and the cron query work. Frontend deployment does not unblock it.
