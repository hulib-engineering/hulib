## Decisions / risks

- **One shared helper, not a 71-site sweep.** The issue was scoped with the user to a single extraction point plus the About flow. The other ~70 `pushError(...)` call sites keep their current behaviour and stay listed as follow-up candidates in the issue. The migration is a one-line change per site once the helper lands, which is why `pushApiError(error, fallback)` takes the translated fallback as an argument instead of reaching for the i18n instance itself.
- **Attaching `.data` to the thrown `Error` is additive but touches the hottest path in the app.** Every non-422, non-304 failure in the codebase flows through `api.ts:152`. The change is strictly an added property, and `error.message` is deliberately left as the `error_contact_admin` key so that the `pushError(t(error.message))` family — which resolves that key through `next-intl` — does not start printing raw English. Sub-task 2 is therefore kept separate from the UI work so it can be reverted on its own.
- **The `error_contact_admin` sentinel is matched by string equality.** `api.ts:152` hardcodes that literal, so the extractor treats it as "no detail" and lets the caller's translated fallback win. If a future change localizes or rewords that literal, the extractor silently stops recognising it and backend detail would be suppressed instead of shown. Worth a comment at both sites rather than a shared constant, because `api.ts` and `utils/apiError.ts` have no import path between them that avoids a cycle.
- **Backend error strings are English and untranslated.** A Vietnamese user sees an English field error inside an otherwise localized UI. Mapping backend codes to i18n keys is out of scope per the issue, and the toast is a 5-second transient surface, so the pragmatic cost is accepted. It is the main thing a user will notice and should be called out in the PR.
- **`WorkEntryForm.tsx` still has no client-side validation,** so the empty `company` payload still round-trips to the server and the toast is the only feedback. The form does not mark the offending field. That is deliberate per the issue's out-of-scope list, but it means this issue fixes *reporting*, not *prevention* — the underlying UX gap (nothing tells the user which input is wrong until after submit) is only half-solved.
- **The UI reference has no measurable spec.** The issue specifies the message text and that fields stack one per line, but no line height, padding or max-width. Sub-tasks 4 and 5 are marked as needing a manual browser check and must be flagged as visually unverified in `docs/results/result-787.md` and in the PR.
