## Decisions / risks

- **The Huber pending-card action was left unanswered at planning time.** Sub-tasks 6 and 9 assume **Accept + Reject**, reusing the existing `MeetingDecisionModal` rather than building a second modal — it already renders the orange "invitation" card and the reason textarea. Read-only cards and a bespoke modal are both cheaper to change now than after sub-task 9 lands.
- **Widening `MeetingDecisionModal` touches shared notification code.** Three call sites depend on it (`MeetingRequestNotification`, `NotificationPopover`, and the new card). Loosening its prop types is low risk in itself, but a regression there breaks notifications rather than this feature, so it is isolated in sub-task 9 and verified there instead of being folded into the card work.
- **`lavender-98` does not exist in the Tailwind theme.** `CARD_CLASS.my_request` at `profile.contant.ts:44` is `bg-lavender-98`, but `tailwind.config.ts:211-215` defines only `lavender` 40 / 80 / 90, so the class resolves to nothing. Nothing depends on the current value — the map was written ahead of this issue and has never been rendered. Sub-task 6 must either add the `98` stop to the config or correct the map, and the result must be checked in a browser: a silently empty background class is precisely what reading the screenshot would not have caught.
- **The design was read from a screenshot, never opened in a browser.** Sub-tasks 6, 7 and 8 are marked as needing a manual browser check, and `docs/results/result-779.md` plus the PR must flag them as visually unverified. Specific unverified values: exact badge pill dimensions, the 24px grid gap, and whether cards in a row align in height under long story titles.
- **`canceled` / `rejected` / `unInitialized` are unreachable today.** None are in the backend's `DEFAULT_STATUSES`, so `resolveVariant`'s `null` branch is defensive only. If the backend later adds them, a Liber loses sight of canceled requests. Out of scope here; worth a follow-up issue.
- **`now` is passed into the resolver rather than read inside it,** which keeps sub-task 5 pure and testable but means no card re-renders as the clock crosses a session boundary — a `right_now` card goes stale until the next refetch or user action. The existing `/my-schedule` has the same property, so this is consistency, not a new regression. A ticking timer would be the fix and is deliberately not in scope.
- **No server-side sort or pagination is added.** Sub-task 1 only makes the existing `offset` param reachable and adds client-side sorting on `startedAt`. With no scroll implementation, a user with more sessions than the current `limit` silently loses the tail. Pre-existing, and out of scope, but it caps how far this feature can be trusted at scale.
- **Sub-task 3 is a large mechanical diff with no behaviour change,** and it lands before any feature code so the new module has a single obvious home. The risk is a mistyped import path in one of 38 files; `check:types` plus `check:deps` is the gate, and it should be committed alone so a revert is cheap.
