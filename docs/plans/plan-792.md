## Decisions / risks

- **Sub-task 5 is the riskiest change in the plan.** It inverts which participant occupies the main stage: today local is the main stage and remote is the picture-in-picture (`AgoraMeeting.tsx:468-496`), and the spec has it the other way round. This changes the default experience for every existing meeting, so it should land as its own commit and be the first thing reviewed in the browser.

- **Attendance stamping is load-bearing and must not move.** `attendReadingSession` fires immediately after `agoraClient.join()` resolves, with a deliberately empty `catch` and an explanatory comment (`AgoraMeeting.tsx:136-145`). The backend marks a session *missed* when the attendance columns are still empty roughly 30 minutes after the meeting ends, so losing this call turns successful meetings into `missed` ones. Sub-task 2 preserves the call, the empty catch and the comment verbatim. The empty catch is **intentional** and must not be "fixed" while the rest of the silent catches in the same file are being cleaned up.

- **The token `'+'` workaround is load-bearing too.** `urlParams.get('token')?.replace(/ /g, '+')` (`AgoraMeeting.tsx:38`) repairs `+` characters mangled into spaces by query-string decoding. Dropping it as an apparent cleanup breaks every join in production, silently. Moving the token to an authenticated endpoint is listed as out of scope in the issue for exactly this reason.

- **Every participant joins with `uid = 0`** (`AgoraMeeting.tsx:134`), so Agora UIDs are not identities. Nothing in the new module may key state, participants or tracks by Agora UID, and attendance continues to be derived from the JWT by the backend.

- **The custom screen picker is the largest and least portable chunk.** Source enumeration via `getDisplayMedia` + `enumerateDevices` behaves well on Chrome and Edge but is inconsistent on Firefox and Safari, which often expose a generic source until a permission prompt is answered. Sub-task 9 therefore specifies a **degrade path to the native picker** instead of an empty grid, and the design's two-column thumbnail grid cannot be guaranteed pixel-identical across browsers. This is flagged for the developer's browser check rather than treated as a blocker.

- **The late-joiner subscribe logic is duplicated inline today** and must be consolidated rather than dropped. `AgoraMeeting.tsx:165-201` walks `agoraClient.remoteUsers` after joining and subscribes to tracks that are already published; without it, a user who arrives second never sees the user already in the channel. Sub-task 2 makes it a single helper and requires both directions to be covered.

- **Two `useSocket` consumers currently refcount the same shared socket.** `AgoraMeeting` and `ChatInCall` each open the default namespace (`AgoraMeeting.tsx:72-82`, `ChatInCall.tsx:52-82`) against the refcounted registry in `src/libs/services/socket.ts`. Consolidating them in sub-task 11 changes socket lifecycle timing, so reaction and chat delivery both need to be exercised with two real browsers — one of the few things here that genuinely cannot be verified statically.

- **Desktop only, per the agreed scope.** All five designs are desktop. `xl` (1280px) is the floor for the new layout and the rail. The existing `< xl` `Popover`-based in-call chat must keep working unchanged so mobile does not regress, but no new mobile layout lands in this issue. Responsive work, including converting rail mode to a bottom thumbnail strip, is an explicit follow-up in the issue's out-of-scope list.

- **All site chrome stays as-is.** `MainTemplate` (`src/templates/MainTemplate.tsx:53-62`) continues to render Header, Footer, MobileBottomNav and MessengerWidget around `/reading`, as agreed. The in-call header row therefore competes with the site header for attention, which is visible in the spec itself but is the agreed behaviour.

- **Recording consent remains asymmetric and unchanged.** The modal is prompted only to the Liber on `user-joined` (`AgoraMeeting.tsx:104-106`); Hubers are never asked. The issue does not ask to change this, but `Schedule.MainScreen.subtitle2` states that recordings require the explicit consent of **both** participants (`src/locales/en.json:1005`). That inconsistency is pre-existing and is deliberately left for a follow-up rather than silently changing consent behaviour in a UI-focused issue.

- **No visual verification is performed by the AI.** Sub-tasks 4, 5, 6, 7, 9 and 10 produce user-visible layout and are each marked as needing a manual browser check, and sub-task 13 requires the result doc and the PR to say so explicitly. Design images live in a gitignored folder and are never committed.

- **Two pre-existing defects outside the meeting room are left alone.** `src/app/[locale]/(auth)/reading/[id]/post-survey/page.tsx:124` gates on `readingSession?.status`, but the `ReadingSession` type declares `sessionStatus`; and `src/features/users/features/schedule/hooks/useScheduleMeetings.ts:66` reads `b.createdAt`, which is not on `ReadingSession`. Neither is in scope, and touching them would widen the diff past the meeting room.
